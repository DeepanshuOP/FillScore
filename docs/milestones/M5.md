# M5 — Trust and reach

Plan: the M5 list in `docs/agent/MASTER_BRIEF.md`; roadmap §3a (5a without C7). Invariants held throughout: past tense only (I1), no model-originated number (I2), correlation not causation (I8), no credential in the repository (I3/I6).

## What a user gets

- **Signed evidence packs.** `GET /api/evidence/pack` returns a pack of the account's own stored measurements (score, order measurements, the public market-data files with their SHA-256, and a limits file). A manifest lists every file with its size and SHA-256 and is signed with Ed25519. Anyone with the published public key can check that no file and no byte of the manifest changed. The account id is not in the pack (a 16-character hash is). Without `EVIDENCE_SIGNING_KEY` the route answers 503 and writes nothing unsigned.
- **A best-execution evidence pack.** `?kind=best-execution` adds an execution summary (how orders ended, shortfall totals, cost against the modelled expectation) and its limits (sample sizes, reference data, what could not be measured). Its text says it "supports your documentation" and states no compliance claim (a test searches every file for such words).
- **Verification you do not have to trust us for.** `scripts/verify_evidence_pack.mjs` checks a pack with Node alone (no install, no network): signature, every file hash and size, missing and extra files, and, with `--key`, the key you trust. Without `--key` it says "consistent" (exit 3): anyone can make a pack that is consistent with their own key. `POST /api/evidence/verify` does the same on the server for small packs, and never answers `valid` without a trusted key.
- **A read-only MCP server** (`mcp-server/`): six tools over the same stored measurements (score, orders summary, exceptions, order replay, rankings, venue comparison). Every tool makes exactly one GET request; a test fails on any other method. Demo accounts work without a token.
- **Ask your execution.** A box on the dashboard (signed-in accounts): "which orders cost the most?" A planner call picks tools by name, code runs them, an answerer writes at most three sentences using only placeholders, and code renders them (so every number is a stored value), removes numbers the model wrote itself, advice, causes, links, markup, invisible characters, other-alphabet look-alikes and any repeat of the prompts, and falls back to a sentence built by code. Two budget units a question; refused before any model call when the allowance is gone.
- **Limits and caching.** The pack and verify routes have their own limiters (20 and 30 per 15 minutes per IP); a pack is cached for a minute per account and kind, so repeated clicks cost one build.
- **Privacy-safe analytics.** One counter per UTC day and event (dashboard view, report download, replay open, quick audit, deep audit, evidence pack download). Nothing else is stored: no account id, no IP, no user agent, no cookie. The page sends nothing when Do Not Track or Global Privacy Control is on.

## What changed in the plan, and why

- **No Promptfoo.** The brief names Promptfoo or an equivalent. The guardrails here are code, so they are tested with models that obey the attack, offline, in the normal pytest job: no model, key or network, and no new dependency. A live run against a real model would add model behaviour but could not weaken these guarantees. A live run can be added if Deepanshu wants one.
- **The server-side verify route is limited to small packs** (the global JSON limit is 10 kb and is a security check I may not change). The proposal is in `.work/proposed/evidence-verify-body-limit.md`; the offline script has no limit.
- **The MCP server needs a token that expires.** FillScore has no long-lived personal API key, a new kind of credential that needs Deepanshu's decision. Demo accounts need none. **Update 2026-11-18: approved and built** (ADR-0016): read-only keys, shown once, SHA-256 hash with a visible prefix, 90-day default expiry, revocable, 5 per user, 60 requests a minute per key, `lastUsedAt`, account-isolated, a Settings section to create and revoke, and `FILLSCORE_API_KEY` in the MCP server.
- **No verify web page.** The route and the script exist; a page belongs to the M8 design pass. **Update 2026-11-18: built, as a minimal page.** `/verify` checks a pack in the browser (`frontend/app/lib/evidenceVerify.ts`): the signature with WebCrypto Ed25519, and with the pinned MIT library `@noble/ed25519` 3.2.0 (strict branch, `zip215: false`) where the browser has no Ed25519; SHA-256 and byte sizes with WebCrypto. The pack is read on the device and never uploaded (an e2e test records every request of the page and checks that none carries any part of the pack). The result says "valid" only when a trusted key (a 16-character fingerprint or a PEM) was given and matches; otherwise "consistent", with the sentence that this does not show where the pack came from. Changing the key re-checks the loaded file at once. Tests: 15 unit tests (RFC 8032 section 7.1 TEST 1 on both engines, a real signed fixture that the offline script also accepts, tampered file, tampered manifest, UTF-8 byte sizes, missing, extra and prototype-named files, wrong key, non-Ed25519 key, unreadable input, forced fallback and an automatic fallback when WebCrypto refuses) and 2 Playwright tests. The offline script and the 10 kb body limit stay as they were.

## Review

Independent `reviewer` subagent on the M5 diff (it ran bypass probes through the real flow). It confirmed the signing and canonical JSON, key handling, account isolation of packs and cache, the tool allowlist, the MCP server's read-only behaviour and Do Not Track handling. It found three high, four medium and several low issues. All are fixed with tests, red first for the red-team cases; the probe strings it used are now part of the red-team.

| # | Finding | Fix |
|---|---|---|
| 1 high | Ask's wording checks were a blacklist: combining, isolate, variation-selector, tag, fullwidth and mathematical-bold characters hid "should"; "will likely", "I suggest", "responsible for", "result of" were not caught. | An answer is shown only if it is plain printable ASCII, holds no number except a tool value, and has none of a wide list of forward-looking, advising or cause-assigning words; otherwise the code-built answer is shown. The claim rules stay as a second line. |
| 2 high | A model's number could pass grounding: "_7 bps" (the markup strip removed the underscore after the check), "t​wo" with an invisible character, "½", "twice". | Every tool value is taken out of the final text; no digit and no number word (zero to ninety, hundred, thousand, half, twice, double ...) may remain. Non-ASCII digits and fractions are refused by the ASCII rule. |
| 3 high | The model received exchange order ids and the user's pasted secrets. The prompt text claimed otherwise. | The "costliest" tool's ids reach the model as "order 1", "order 2"; code puts the real id in. Tokens, e-mail addresses, key-like strings, long hex ids and long digit runs in the question are replaced before it is sent. Tests read the user message too. |
| 4 medium | The server verify route cannot check a real pack (10 kb body limit). | Unchanged: it is a security check and needs Deepanshu (item 13, `.work/proposed/evidence-verify-body-limit.md`). The offline script is the check for real packs. |
| 5 medium | A pack signed with an attacker's own key read "valid". | The route and the script say "consistent", not "valid", unless the pack was signed by the trusted key; the script exits 3 for "consistent, origin not shown". |
| 6 medium | A manifest naming "constructor" made the check throw (an `in` lookup). | Own-property lookups; the file size in the manifest must be the file's size; tests with "constructor", "toString", "__proto__". |
| 7 medium | A question could take three model calls for two units, and an empty question was charged. | No regeneration (two calls, always); an empty question is answered before any charge. |
| low | MCP followed redirects; the public-key route called any key Ed25519; big packs sat in memory; analytics counters can be inflated by many IPs. | `redirect: 'error'`; only an Ed25519 key counts as configured; packs over 2 MB are not cached and the cache holds 50; the counter limit is per IP and the storage is bounded (days x 6 events): stated, not changed. |

Red-team after the fixes: 178 offline cases (32 hostile model answers x 5 plans, 16 hostile questions, 2 more) hold every invariant.
